# 秒杀可靠性与压测记录

## 本次测量口径更新（2026-11-05）

版本说明（2026-11-06 补记）：本轮记录以 `main` 分支 `a03a610` 的业务代码为基准，
测量脚本 `VoucherSeckillLoadIT` 包含当时工作区中的未提交改动，因此不能仅检出 `a03a610` 就视为还原了本轮测量工具。
各轮报告以其实际包含的字段为准；当前脚本并非每一轮执行时的精确快照。
本次补记没有重新执行测试，也不改变下方历史报告及结果。

历史数据保留在下方，不与新增测量混为同一批结果。本轮不修改秒杀业务策略，先补齐测量：

- **HTTP 响应耗时**：客户端开始 `send()` 到收到响应，包含受理和库存不足等业务拒绝；不包含客户端线程池中等待执行的时间。
- **请求到数据库可见**：同一次请求开始到后台观察线程首次查询到订单；仅对受理订单统计。
- **请求到 SUCCESS 可见**：同一次请求开始到观察线程首次读取到成功状态；这不等于前端轮询实际显示耗时。
- **请求结束后的排空时间**：全部 HTTP 请求结束到最后一个 SUCCESS 被观察到，若此前已观察完成则记 0；未全部观察完成记 N/A。
- **消费者处理时间**：现有 Micrometer Timer 的处理均值/最大值，包含用户锁、数据库事务、状态更新和 ACK，不包含排队时间；不是单独的 SQL 耗时。
- **结束快照**：Pending、consumer lag、重试、补偿与 DLQ；结束时为零不能证明过程中没有积压。

后台观察线程每轮查询该券的订单 ID，只对尚未观察成功的 ID Pipeline 查询状态，然后休眠 100 ms。
因此数据库和 SUCCESS 可见耗时是包含采样延迟的上界，误差还包括查询本身耗时，不能简单视为固定 ±100 ms。
观察查询会增加负载，新旧脚本测出的数字不宜直接计算性能提升百分比。

异步排空超时现在先生成 FAIL 报告，再触发测试断言；每轮报告除最新文件外，还归档到
`target/load-reports/<时间>-c<并发>-r<请求>-s<库存>.md`，避免下一轮覆盖证据。
非 200 HTTP 响应、网络/解析错误与缺失受理订单 ID 均计入请求错误，不再作为正常业务拒绝。
报告还记录请求错误分类，以及可配置的建连/请求超时预算（默认 5000/10000 ms）。
因此历史的“传输成功率”不能直接等同于新口径下的全部 HTTP/client 请求成功率。

脚本在本轮测量期间继续补充了诊断字段：`2026-11-05-c100.md` 和 `2026-11-05-c500-first.md`
未记录请求错误分类及建连/请求超时配置字段；`2026-11-05-c500-diagnostic.md` 和
`2026-11-05-timeout-budget.md` 包含这些字段。归档保留原始内容，不按当前脚本补造旧轮次的诊断数据；
首轮 500 并发的 97 次请求错误仍标为未分类，不能根据后续复测推定其全部为 `ConnectException`。

### 同等负载的并发对比

以下两档保持请求数、库存和预期受理比例相同，只改变客户端并发；每次使用独立容器，结果仍包含各自 JVM 冷启动影响。
它们用于本机定位，不能当作严格的稳定态容量上限或优化前后收益。

```powershell
mvn '-Dtest=VoucherSeckillLoadIT' '-Dload.requests=500' '-Dload.stock=200' '-Dload.concurrency=100' test
mvn '-Dtest=VoucherSeckillLoadIT' '-Dload.requests=500' '-Dload.stock=200' '-Dload.concurrency=500' test
```

默认数据库排空预算为 HTTP 窗口后的 30 秒，随后成功状态观察再给 15 秒。
可用 `-Dload.db-drain-ms=<毫秒>` 和 `-Dload.status-drain-ms=<毫秒>` 调整预算；比较不同轮次时必须保持预算一致。
报告中的完成时间分位数仅覆盖已观察的订单，超时或采样失败时必须同时查看样本数和排空标记。
订单数、库存、状态与 Stream 诊断分步读取，失败报告不是跨 MySQL/Redis 的原子快照。

### 如何据此定位

1. HTTP P95 高、SUCCESS 与数据库耗时接近：检查入口 Redis/会话续期、HTTP 连接与线程排队，以及消费者数据库链路；不能直接归因某一条 SQL。
2. HTTP 快而完成时间长：优先检查异步排队。结合单线程消费者处理均值、总处理数和排空时间，区分受理速度与消费速度。
3. 数据库可见后仍长时间没有 SUCCESS：检查状态写入、异常重试；Timer 包含 ACK，但观察到 SUCCESS 本身不代表 ACK 已完成。
4. 重试或 Pending 非零：先分析失败/接管路径，不能把这批数据直接当正常吞吐基线。

## 2026-11-05 实测对比

常规回归另执行 `mvn -B test`，结果为 **27 tests、0 failures、0 errors、0 skipped**，含 8 个容器用例，
见 [逐类统计](performance/2026-11-05-regression.txt)。该命令默认不运行 `VoucherSeckillLoadIT`，因此不能用常规回归通过覆盖下列高并发压测失败。

环境：Windows + Docker Desktop 29.6.1，JDK 17.0.19；单应用实例，Testcontainers MySQL 8.0.36、Redis 7.2。
宿主 CPU 为 AMD Ryzen 9 7945HX（16 核、32 逻辑处理器）；Docker 报告 32 CPU、约 7.60 GiB 内存。
三轮均为 500 请求、200 库存，默认建连 5 秒、请求 10 秒、数据库排空 30 秒、状态观察额外 15 秒。
三轮没有同时运行其他本项目测试，每轮独立容器与 JVM；未做稳定态预热，硬件与宿主机负载未固定。

| 轮次 | 并发 | HTTP 窗口吞吐 req/s | HTTP P95 | SUCCESS 可见 P95 | HTTP 后排空 | 处理均值/条 | 请求错误 | 结果 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| [基线](performance/2026-11-05-c100.md) | 100 | 191.72 | 2.04 s | 7.42 s | 7.25 s | 39.19 ms | 0 | PASS |

HTTP 吞吐和分位数统计所有请求（包括业务拒绝及错误），并不是订单完成吞吐。三轮均受理 200 单，最终数据库订单数与
SUCCESS 状态数均为 200，双端剩余库存均为 0，重试/补偿/DLQ 均为 0，结束 Pending/lag 均为 0。
高并发档仍因请求错误而失败，不能将订单最终一致描述为全链路压测通过。

### 证据支持的定位与限制

- **已观察到消费排队**：100 并发 HTTP 窗口结束后仍需约 7.25 秒才观察到全部 SUCCESS。
  单消费者处理 200 条、每条均值约 39.19 ms，对应约 7.84 秒累计处理时间；与请求完成后的尾部积压方向一致。
  500 并发两轮每条处理均值约 49～50 ms，完成 P95 进一步上升。当前单线程消费处理链路是主要排队点。
- **已观察到请求建连失败**：分类复测的 37 次请求错误均为 `ConnectException`，不能当作库存不足。
  错误发生在客户端 HTTP 调用的连接层；现有证据还不能进一步确定是宿主机/WSL 网络、监听队列、连接建立负载还是其他具体原因。
- **没有单独归因 SQL**：数据库可见与 SUCCESS 可见 P95 接近，未见额外数秒的状态写入尾延迟。
  但消费者 Timer 同时包含锁、数据库和 Redis；若继续优化，需要分段追踪后再决定改数据库、连接或消费并行度。
- **没有宣称性能提升**：本轮改变测量与错误统计，未调整业务消费策略。新旧历史数字和两次高并发波动不能写成优化收益。

## 历史压测记录（2026-08）

## 测试环境

2026-08-08 在本机 Docker Desktop 环境执行阶梯压测。

- 应用：Spring Boot 3.4.4，随机 HTTP 端口，单应用实例
- 依赖：Testcontainers 1.21.4、MySQL 8.0.36、Redis 7.2
- JDK：17.0.19
- Docker Engine：29.6.1，分配内存约 7.8 GB
- 请求客户端：JDK `HttpClient`，单请求超时 10 秒

## 阶梯压测结论

| 并发 | 请求 | 初始库存 | 业务成功率 | 请求窗口 | 吞吐量 | 平均延迟 | P50 | P95 | P99 | 结果 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 100 | 500 | 200 | 40.00% | 3.75 s | 133.29 requests/s | 704.10 ms | 76.41 ms | 3.23 s | 3.23 s | PASS |
| 200 | 1000 | 400 | 40.00% | 6.07 s | 164.64 requests/s | 1140.97 ms | 158.20 ms | 5.10 s | 5.10 s | PASS |
| 500 | 2000 | 400 | 20.00% | 8.89 s | 225.09 requests/s | 2070.79 ms | 401.56 ms | 7.30 s | 7.34 s | PASS |
| 500 | 2000 | 800 | - | - | - | - | - | - | - | 30 秒内未排空 |

三个通过档的 HTTP 传输成功率均为 100%，且秒杀受理数、MySQL 最终订单数、Redis `SUCCESS` 状态数完全一致，
MySQL 与 Redis 剩余库存均为 0，没有发生超卖。

结果表明：

1. 入口链路可以承受本机 500 并发、2000 个请求，Redis Lua 库存校验在通过档保持一致；
2. 并发从 100 增加到 200 时，吞吐量提高约 23.5%，但 P95 从 3.23 秒上升到 5.10 秒，排队已明显加重；
3. 500 并发、400 库存档虽然通过，但 P95 已达到 7.30 秒，不适合作为低延迟运行点；
4. 500 并发、800 库存档在请求结束后 30 秒内没有满足“最终订单数等于 HTTP 受理数”的等待条件，测试在生成指标报告前失败。
   这说明异步落库排空或请求确认已超过当前测试阈值，但不能单凭该断言判定数据丢失、超卖或最终不一致；
5. 500 并发通过档只有 20% 的请求被受理，其余请求走较轻的库存不足拒绝路径，因此其吞吐量不能与 40% 业务成功率的
   100/200 并发档直接等价比较。

如果以 P95 小于 5 秒作为当前环境的临时目标，建议把单实例并发控制在约 100；更高峰值应配合入口限流、积压监控、
异步消费者扩展或应用水平扩容。该建议只适用于本机回归环境，不是生产容量承诺。

## 指标口径

吞吐量和延迟只统计 HTTP 请求处理窗口，不包含 Testcontainers 拉起、数据库初始化、Spring Boot 启动以及请求后的异步排空时间。
HTTP 请求完成后，测试最多等待 30 秒让订单消费者落库，再等待最多 15 秒确认 Redis 订单状态，最后校验：

- HTTP 传输错误数为 0；
- 秒杀受理数等于初始库存；
- MySQL 最终订单数和 Redis `SUCCESS` 状态数等于初始库存；
- MySQL 与 Redis 剩余库存均为 0。

所有条件同时成立才记为 `PASS`。测试关闭容器时可能出现 Lettuce/Hikari 的断连或重连警告；若这些日志出现在报告输出之后，
且 Surefire 最终为 `BUILD SUCCESS`，它们属于测试依赖回收阶段的日志，不是压测失败。

## 可靠性覆盖

`VoucherOrderReliabilityIntegrationTest` 使用真实 MySQL 与 Redis 验证：

1. 死亡消费者留下的 Pending 消息可以被另一消费者通过 `XAUTOCLAIM` 接管；
2. 40 个并发请求争抢 20 份库存时不超卖，受理数、订单数、状态数和库存一致；
3. 数据库连续处理失败达到上限后，订单标记为 `FAILED`，Redis 库存和购买标记由 Lua 原子补偿，原消息 ACK，并写入有界 DLQ。
