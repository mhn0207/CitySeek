## 商户混合读

流量由 80% 已预热的店铺详情和 20% 附近商户查询组成，后者轮询 32 组坐标与类别组合。k6 检查详情的商户 ID，检查 GEO 返回 5 条对应类别、5 km 内的记录。GEO 先查 Redis，再从 MySQL 取回 5 条商户详情。

| 目标请求/秒 | 时长 | 实际请求数 | 实际请求/秒 | 详情 P95 | GEO P95 | HTTP/内容失败 | k6 漏发 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 250 | 25 s | 6,251 | 250.0 | 3 ms | 8 ms | 0 | 0 |
| 500 | 25 s | 12,500 | 499.9 | 4 ms | 7 ms | 0 | 0 |
| 1,000 | 25 s | 25,001 | 999.9 | 8 ms | 10 ms | 0 | 0 |
| 1,500 | 25 s | 36,901 | 1,475.2 | 104 ms | 107 ms | 0 | 598 |
| 2,000 | 25 s | 46,793 | 1,859.6 | 211 ms | 212 ms | 0 | 3,208 |
| 500 | 120 s | 60,001 | 500.0 | 4 ms | 8 ms | 0 | 0 |
| **1,000** | **120 s** | **120,001** | **999.96** | **5 ms** | **7 ms** | **0** | **0** |
| **1,500，调整 k6 后** | **120 s** | **180,001** | **1,499.96** | **8 ms** | **8 ms** | **0** | **0** |

延迟由 k6 按客户端发出 HTTP 请求到收到完整响应计算。漏发是 k6 在目标速率下未能启动的迭代，在 2,000 档观察到压测端达到 350 个 VU 上限。`docker stats` 的采样峰值显示，Redis 在 1,000、1,500、2,000 档的 CPU 占用分别为 64.92%、94.49%、100.63%，其中 100% 约为一个逻辑处理器。高档出现了排队信号，服务与压测端共享同一虚拟机，CPU 采样也有间隔。

1,000 请求/秒的 120 秒复测前先预热 15 秒。96,001 次详情请求和 24,000 次 GEO 请求的 P99 分别为 9 ms 和 10 ms。该轮 MySQL 的 120,000 次 `tb_shop` 取行与每次 GEO 回表取 5 行相符。

在 1,500 请求/秒档，将 k6 的预分配 VU 从 100 提高到 400、上限从 350 提高到 650，进行 25 秒诊断复测。混合读实际 1,499.69 请求/秒，37,501 个响应全部有效、0 漏发，详情和 GEO P95 分别为 8 ms、9 ms。同一速率的纯缓存详情诊断中，37,501 个响应全部有效、0 漏发，P95 为 2 ms，MySQL 取行数为 0。两种流量各采样 4 次，Redis 的 CPU 采样峰值分别为 80.57% 和 18.69%。两次混合读的差异提示，在推断后端容量时需要同时检查 k6 的发压行为与服务端资源。

随后使用调整后的 k6 配置预热 15 秒，再按 80% 详情、20% GEO 连续发压 120 秒。**实际吞吐为 1,499.96 请求/秒，180,001 个响应均有效，0 HTTP 错误、0 漏发。** 144,001 次详情和 36,000 次 GEO 的 P99 分别为 15 ms 和 16 ms。该轮 MySQL `tb_shop` 取行数为 180,000，与 GEO 回表规模一致。

## 秒杀与订单一致性

每轮重建应用和网关容器，先用 100 个用户和 50 张券预热，再对新券派发 500 个虚拟用户各一次下单。按 4、1、1、4 个消费者交叉执行四轮。消费者每批读取 16 条消息，Pending 接管阈值为 30 秒，扫描间隔为 5 秒。四轮最后一个下单请求在对应 k6 场景启动后 153～382 ms 发出。

入口 P95 统计所有下单请求。成功可见 P95 统计受理订单，从开始下单到客户端首次经状态接口查到 `SUCCESS`，含约 250～340 ms 的轮询间隔。排空时间从最后一个下单响应返回计到最后一个 `SUCCESS` 被观察到。

| 轮次 | 消费者 | 入口 P95 | 成功可见 P95 | 入口结束后排空 | 实际订单 | 请求错误 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 4 | 181 ms | 2.71 s | 2.64 s | 200 | 0 |
| 2 | 1 | 312 ms | 6.18 s | 6.11 s | 200 | 0 |
| 3 | 1 | 801 ms | 6.22 s | 5.79 s | 200 | 0 |
| 4 | 4 | 318 ms | 3.54 s | 3.40 s | 200 | 0 |

两组对照中，4 个消费者使订单 `SUCCESS` 可见 P95 分别下降 **56.1%** 和 **43.1%**。每轮都是 200 笔受理、200 笔 MySQL 落库、200 个 Redis `SUCCESS`、300 次库存不足，Redis 和 MySQL 库存都为 0。每轮结束时 Pending、消费滞后、重试、补偿与死信均为 0。另用同一用户突发提交 50 次请求，库存为 20，结果为 1 单成功、49 次重复拒绝，Redis 和 MySQL 库存均剩 19 张。

另测目标 250 次下单/秒、20 秒、2,000 张券，状态观察仍走 HTTP 轮询。首轮预分配 250 个 k6 VU，实际收到 3,998 个下单请求，k6 漏发 1,003 次迭代。这一轮未达到目标发压。端上共观察到 2,000 笔 `SUCCESS`，MySQL 和 Redis 对账一致，成功可见 P95 为 16.24 秒。最后一个下单响应返回后 9.00 秒观察到最后一笔 `SUCCESS`。k6 在时间边界多调度了一个请求槽位。

复跑将 k6 预分配 VU 调至 1,600、上限调至 2,000。20 秒内发出 **5,000 个下单请求**，共收到 2,000 个受理和 3,000 个库存不足响应。客户端、数据库和 Redis 核对到 **2,000 笔成功、0 超卖**，HTTP 错误、漏发、重试、补偿、死信和结束 Pending / lag 均为 0。入口 P95 为 **8 ms**，受理订单 `SUCCESS` 可见 P95 为 **15.53 秒**，从最后一个下单响应到最后一笔 `SUCCESS` 被观察到耗时 **4.32 秒**。应用消费计时器平均每笔 47.94 ms，包含锁、数据库和 Redis 等操作。批量秒杀场景中，订单等待和状态轮询显著增加了用户观察到的完成时间。

## Feed Outbox 扇出

为单个作者建立 5,000 条合成关注关系，通过 Nginx 上传测试图片并依次发布 5 篇笔记。每轮开始于调用发布笔记接口，结束于观测到 MySQL Outbox 的 `SUCCESS`，计时包含调度和数据库轮询采样间隔。应用按每批 200 名粉丝写入 Redis，Outbox 调度间隔为 1 秒。

| 发布轮次 | 发布接口耗时 | 观察到 Outbox 成功 | Redis 实际送达 |
| ---: | ---: | ---: | ---: |
| 1 | 49.4 ms | 0.98 s | 5,000 / 5,000 |
| 2 | 28.8 ms | 0.99 s | 5,000 / 5,000 |
| 3 | 36.1 ms | 0.48 s | 5,000 / 5,000 |
| 4 | 31.2 ms | 1.08 s | 5,000 / 5,000 |
| 5 | 32.6 ms | 1.63 s | 5,000 / 5,000 |

逐条校验了 25,000 个 Redis 有序集合成员，5 个 Outbox 事件重试均为 0。HTTP 抽查时，关注者可见对应笔记，未关注用户的 Feed 无该笔记。

## 简历表述

- 基于 Redis 缓存和 GEO 索引实现店铺详情与附近商户查询。在 Docker 单实例、10 万条合成商户数据上用 k6 持续压测 120 秒，混合读约 1,500 请求/秒，两类查询 P95 均为 8 ms，0 错误、0 漏发。同一批店铺的冷热对照中，MySQL 取行次数由 6,000 降至 0。
- 基于 Redis Lua 和 Stream 实现秒杀库存预扣、异步落单与一人一单。500 个虚拟用户抢购 200 张券，四轮均落库 200 单、0 超卖。将消费者从 1 个增加到 4 个，两组对照的订单成功可见 P95 下降 43%～56%。
- 使用事务 Outbox 和 Redis Pipeline 实现关注 Feed 推送。单作者 5,000 名合成粉丝、5 次发帖，逐条核实 25,000 次投递，单篇 Outbox 完成观察耗时 0.48～1.63 秒。

## 复现

前提是启动 Docker Desktop 并使用 Linux 容器，准备 Python 3.12，从项目仓库根目录执行。证据压缩包的 `scripts` 目录含 `run.py`、`seed.sql`、`read.js` 和 `seckill.js`。将四个文件复制到空目录 `target/perf-rerun`，使用独立 Compose 项目与初始数据库。

```powershell
$env:CITYSEEK_BENCH_PROJECT = 'cityseek-perf-rerun'
$env:APP_PORT = '18081'
$env:WEB_PORT = '18080'
$env:WEB_BIND_ADDRESS = '127.0.0.1'
docker compose -p $env:CITYSEEK_BENCH_PROJECT up --build -d --wait --wait-timeout 180
docker pull grafana/k6:0.57.0
python -X utf8 target/perf-rerun/run.py seed
python -X utf8 target/perf-rerun/run.py reads
python -X utf8 target/perf-rerun/run.py seckill
python -X utf8 target/perf-rerun/run.py feed
python -X utf8 target/perf-rerun/run.py diagnose
python -X utf8 target/perf-rerun/run.py sustained
python -X utf8 target/perf-rerun/run.py upper-read
docker compose -p $env:CITYSEEK_BENCH_PROJECT stop
```

在 `data.json` 核对商户、用户和 Redis GEO 成员数。用 `*-verified.json` 核查各轮请求数、延迟分位数、错误，以及 MySQL 和 Redis 的对账结果。原始 k6 JSON、资源采样 JSONL 和逐轮日志也保存在证据包中。按需单独运行 Maven 回归，避免与性能负载并行。所有性能数字适用于上述单机配置、合成数据和流量模型。测试完成后停止了隔离容器，测试卷保留。
